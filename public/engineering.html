How TaskOps works.

A compact technical walkthrough of the system boundaries, persistence model, API contracts and workflow invariants. This is an engineering demo built around AI-data operations workflows; all seeded people and tasks are synthetic.

01 · Architecture

TaskOps is a small full-stack application with a static browser client, HTTP function layer and PostgreSQL as the source of truth. The browser never writes directly to the database.

Browser UI (HTML / CSS / JavaScript)
          │
          ├── Signed-in read requests ──→ API functions
          │                                  │
          └── Signed-in mutations ───────────┤
                                         ▼
                                PostgreSQL
                         ┌──────────┬──────────┐
                         │ tasks    │ reviews  │
                         │ reviewers│ events   │
                         │ imports  │ indexes  │
                         └──────────┴──────────┘

The frontend renders server-owned state. Workspace reads and writes require a signed-in end-user session; health and session-introspection endpoints expose no workspace records. The server resolves the active workspace from the authenticated user’s organization membership, never from a browser-supplied workspace ID. Every write is validated by an API handler, persisted to PostgreSQL, and accompanied by an event record.

Design principle: keep task state and review evidence in the database; make the browser a thin operator interface; keep state changes explicit and auditable.

04 · Workflow state machine

queued ──assign──→ in_review
                       │
              ┌────────┼────────┐
              ▼        ▼
        needs_revision  rejected
              │
              └──re-queue──→ queued

A passing review submission (not the generic transition API)
is the only path from in_review to awaiting_approval:
in_review ──score ≥ 85──→ awaiting_approval ──approve──→ approved
           approved

Allowed transitions are enforced server-side.
approved and rejected are terminal in this demo.

Review submission does not itself approve a task. A passing review moves the task to awaiting_approval; a separate approval action is required. A revision request re-enters the revision queue, and re-queueing increments the revision counter. The API rejects stale concurrent transitions when the current status no longer matches the status read before the update.

05 · Quality scoring contract

Each dimension is rated from 1 to 5. Weighted score is computed as the weighted sum divided by 5, multiplied by 100.

score = (
  correctness             × 0.30 +
  completeness            × 0.20 +
  instruction_adherence   × 0.20 +
  format_validity         × 0.15 +
  evidence_quality        × 0.15
) / 5 × 100
VERDICTRULENEXT STATE
passScore ≥ 85 and every dimension ≥ 3.awaiting_approval
reviseScore 50–84.99 with no critical dimension below 2.needs_revision
failScore below 50 or any dimension below 2.needs_revision (explicit reviewer/lead action still decides final rejection).

The human-review rubric remains deterministic. The separate evaluation engine supports versioned JSON Schema checks, a versioned rubric snapshot, gold-example context and per-task evidence. Deterministic validation needs no provider key. Hybrid mode uses an independent LLM judge when configured and falls back to deterministic checks when unavailable; AI-only mode fails clearly without a provider. Evaluation results never change task workflow state or approve work.

06 · Data ingestion

The UI accepts CSV and JSON arrays up to 100 records per batch. CSV parsing supports quoted cells and escaped quotes. API validation is repeated server-side; client checks are not trusted.

CSV fields: external_id,title,description,project,queue,task_type,priority,payload. The payload field may be omitted or contain JSON. Missing external IDs are generated for the batch. Existing external IDs are skipped idempotently rather than overwriting work.

curl -X POST /api/tasks/import \
  -H "Content-Type: application/json" \
  -d '{
    "source": "sample.csv",
    "records": [{
      "external_id": "DEMO-001",
      "title": "Check source grounding",
      "project": "Atlas Evaluation",
      "priority": 4,
      "payload": {"source": "synthetic"}
    }]
  }'

Response includes submitted, inserted, duplicates, rejected and row-numbered errors. Trace ingestion is a separate bearer-key endpoint: it accepts up to 250 spans and 750 KB per batch, redacts secrets/prompt/PII-like attributes before storage, returns HTTP 202, and normalizes OTLP JSON or custom spans asynchronously.

07 · Security model

  • Workspace data reads and mutations declare access = "user"; only health and session introspection remain public.
  • The server resolves the workspace from req.user.id and an active organization membership; the browser cannot choose a workspace ID.
  • Membership roles are stored as an opaque-user-ID TEXT relation: owner, admin, member, reviewer, quality lead or auditor. Write routes enforce role allowlists.
  • Every operational record is scoped to a workspace. Composite foreign keys prevent cross-workspace task/reviewer, review/task and event/task relationships.
  • Reviewer assignments serialize capacity checks and record the event atomically.
  • Reviews and task events reject updates/deletes, including parent-row cascades.
  • SQL uses parameterized values; payloads are size-bounded and stored as JSONB. Login uses platform-managed email codes/passkeys.
  • Current records are synthetic; no client data or real customer information is present.
The v18 MVP includes collaboration, linked reviewer workflows, deterministic evaluation, hybrid fallback and bearer-key trace ingestion. It is still a private prototype, not a production-certified multi-tenant SaaS: complete real-browser email/passkey and legitimate invitation acceptance; connect Anthropic for semantic AI judging; change project visibility to Public before external users or trace senders can reach it; add rate limits/quotas, retention/deletion, independent tamper-evident audit retention, backups, deeper database row isolation and production monitoring before customer data is used.

09 · Engineering trade-offs and next steps

  • Current: authenticated workspace bootstrap, membership-derived tenant scoping, composite cross-workspace foreign keys, basic role allowlists, serialized reviewer assignment, append-only review/event records, simple status workflow and synthetic seed data.
  • Current: team invitations/member administration, workspace switching, default rubric seeding, versioned schema/rubric/gold data, deterministic and hybrid evaluation runs, scoped trace keys, async trace ingestion, redacted trace storage, AI usage and workspace JSON exports.
  • Next: real browser/mailbox sign-in acceptance, provider setup for AI judging, production rate limiting, retention/deletion, stronger operational-table row policies, dashboards/alerts, automated test suite and connector SDK packaging.
  • Scale: scheduler-backed async jobs are sufficient for the current prototype. Replace with a dedicated durable queue and columnar analytics store only when throughput warrants it; retain bounded reads and batch imports.
  • Observability: trace ingestion and basic workspace exports are implemented. Still add service-level dashboards, alerting, retention controls, and larger-scale analytics before production.

10 · Collaboration and workspace management

Organizations can contain multiple workspaces. Authenticated users receive workspace memberships; the active workspace is resolved server-side from the user's identity and membership, while a requested workspace ID is only a selection hint that must pass a membership check.

  • Workspace switcher and create-workspace route.
  • Organization member and active-workspace member directories.
  • Organization roles (owner/admin/member) are separate from workspace roles (owner/admin/member/reviewer/quality lead/auditor); changing one does not silently change the other.
  • Workspace role downgrade from Reviewer/Quality Lead is blocked while that member's reviewer profile has open tasks; after reassignment the profile is deactivated.
  • Reviewer profiles are linked to active workspace members, with capacity/specialty updates and safe deactivation. Reviewers may only submit reviews for tasks assigned to their own profile.
  • Workspace-only member removal and organization-wide member removal are separate actions, with owner/admin restrictions and last-owner protection.
  • Seven-day invitations with single-use, SHA-256-hashed tokens bound to the invited email; invitations can be revoked.
  • Free-tier email restrictions may prevent delivery. In that case the API returns a copyable invitation URL.

11 · Evaluation engine

Task schemas, rubric versions and gold examples are workspace-scoped. An evaluation run snapshots the active rubric, relevant task schemas and gold examples at creation time, then processes tasks asynchronously.

  • Deterministic mode validates task context, required JSON fields, supported property types, enums, string length bounds and additional-property rules.
  • AI mode uses an independent evaluator; hybrid mode blends deterministic checks and the AI judge. Model output is validated and never approves or changes a task.
  • Without an Anthropic API key, hybrid mode records provider_not_connected and falls back to deterministic evidence; AI-only runs fail clearly.
  • Each result stores score, verdict, dimensions, rationale, evidence, model/evaluator metadata and the rubric/schema versions.

12 · Integrations and observability

Workspace owners/admins/quality leads can issue and revoke scoped bearer keys. The public trace receiver requires a valid traces:write token, accepts OTLP JSON or custom span batches, enforces batch bounds, redacts sensitive key/value attributes before queue persistence and schedules normalized storage.

  • Trace batches return HTTP 202 and are processed by a scheduler worker; spans are unique by workspace + trace ID + span ID.
  • Trace explorer shows recent spans and batch state; task, evaluation and trace JSON exports are workspace-scoped and capped at 500 rows per request.
  • AI usage is filtered to active members of the workspace. AI usage and model judging require a provider setup; no provider key is currently connected.
  • The project is still on PostgreSQL and Hatchable scheduler infrastructure; a dedicated ClickHouse store, external S3-compatible payload archive and enterprise OTel collector are future scale steps, not present capabilities.
